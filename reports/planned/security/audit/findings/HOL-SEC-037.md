# HOL-SEC-037: Call signals were bound by call id alone, and a share could be re-pointed by any participant

```

Boundary:    TB-2 (peer <-> peer)
Traces to:   C-16; candidates M1, M2, M3 (evidence media:S-02, S-03, S-09)
```

## Description

Every inbound 1:1 call signal was matched to the live call by its call id only,
never by who sent it, and the id came from `Random()`. An `audio_state` with no
call id applied to whatever call was live.

The voice-channel origin guard accepts an origin naming the sender or ourselves.
That is right for an answer, but a screen assignment must come from the share's
originator: with "or ourselves", any participant could assign viewers to our own
sibling's share. A feed report goes the other way (feeder to owner) and must name
our stream, not the sender's.

## Reproduction

`test/call_signal_sender_test.dart`, `authz_only_a_friend_or_our_own_device_rings_us`,
`authz_a_share_is_assigned_by_its_originator_and_reported_to_its_owner`
(node/voice_handler.rs tests).

## Fix

- `handleCallSignal` drops every signal but an invite unless its sender is the
  same person as the live call's peer (device or master, collapsed).
- Call ids come from `Random.secure()`; `audio_state` must name the live call.
- A screen assignment's origin must be its sender; a feed report's origin must be
  one of our own devices.
- M2 (decided 2026-09-27): only an accepted friend or our own device rings us.
  The app only ever offered calls between friends, but the receiver checked
  nothing beyond the block list, so any identity with an Olm session (a stranger
  who shared a room with us) could ring us from a modified client.
  `call_invite_allowed` now drops every other invite, which ends the call flow.

## Test

`authz_only_a_friend_or_our_own_device_rings_us` (node/voice_handler.rs tests)
covers M2. All three tests fail with the old rule put back and pass with the fix.
Full suites green.
