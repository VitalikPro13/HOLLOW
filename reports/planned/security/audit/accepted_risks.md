# Accepted risks

What we knowingly do not defend against, why, and when we look again. An
entry here is a decision, not an oversight: each has an owner and a reason
that survives a professional auditor reading it.

| ID | Risk | Decision | Reason | Owner | Review |
|---|---|---|---|---|---|
| AR-01 | The relay has no per-message rate limits, although ASVS 17.3.1 wants signalling to survive floods and RFC 9420 16.8 says KeyPackage requests SHOULD be rate-limited. | Accepted (2026-09-26) | Message and binary rate limits were tried and broke the core: a reconnect burst (sync requests, channel probes, profiles, signalling) exceeds any limit, and dropped frames wedge CRDT sync. The protections that stay: per-IP connection caps (34 per IP, 10 new per minute, IPv6 /64), guest mode with its own limits and room cap, CAKE per-host fair share on the NIC, coturn locked to the relay's own peers, the 64 MB payload ceiling and hard backpressure. Memory: `feedback_relay_rules`, `project_relay_ip_limits`, `project_relay_fairshare_turn_lock`. | Vitalik | When flood tests exist (phase F, WP4): measure what a single authenticated peer can make the relay or other clients do. |
| AR-02 | Every device holds the master key, so a stolen usable device can revoke its owner's real devices (they wipe themselves), issue destroy orders, and keep the identity. | **Not accepted: fixed by design ID-1** (2026-09-26) | The recovery phrase, never stored on any device, becomes the root of authority. See the plan's section "Identity authority design". Until ID-1 ships the whitepaper's "Stolen/lost device" row must not promise more than this. | Vitalik | When ID-1 ships (target 0.12). |
| AR-03 | Inside a group call, any participant can forge media frames that appear to come from another participant (RFC 9605 7.2, shared SFrame keys). | Accepted (2026-09-26) | As far as we know, no mainstream E2EE call system (Signal, WhatsApp, Meet, Zoom) signs individual frames; all share symmetric frame keys among participants. The forger must be an admitted participant running a modified client. Per-frame signatures cost CPU on every phone. Outsider protection (nonce uniqueness, lead L-01) is NOT covered by this entry and must be verified. | Vitalik | If a mainstream system ships per-frame sender authentication. |
| AR-04 | Traffic analysis, relay availability, post-quantum, trust on first use, a compromised unlocked running device. | Accepted | Listed in WP 23.2 and claims.md "What we do not promise". | Vitalik | At each whitepaper revision. |
| AR-05 | Any peer in a room we share can ask us for an asset by its hash (server emotes, stickers, GIFs, banners, avatar frames and animations, personal emotes), learn whether we hold it and receive its bytes (candidate H20). | Accepted (2026-09-27) | Assets are content-addressed: knowing a hash almost always means the asker has already seen the asset, since server emotes live in the server's state and profile media hashes ride the profile updates people already receive. The requests travel in plaintext, which the class A work moves into encrypted transport. | Vitalik | With the class A design. |
| AR-06 | Every `FileRequest` re-encrypts and re-streams the whole file, so a peer entitled to a file can make us upload it repeatedly (candidate H21). | Accepted (2026-09-27) | Honest clients ask only when they need the bytes (a download, a decrypt-fail retry). Only an entitled requester (the DM counterpart, or a member who can read the channel) is served, the per-sender frame budget bounds the rate, and a dedup window would break the retry. | Vitalik | With the relay traffic measurement in phase G. |
| AR-07 | Once the relay's offline buffer holds its global ceiling of 65,536 recipient keys, a sender holding a single key evicts the oldest deposit of anyone, so many throwaway accounts can push real parked messages out (candidate I9). | Accepted (2026-09-27) | The buffer is an availability cache: an evicted message is not lost, the sender still holds it and sync delivers it once both sides are online. Filling it needs tens of thousands of accounts across many IP addresses (34 connections and 10 new per minute per IP). A refusing quota is the rule-breaking fix (`feedback_relay_rules`). | Vitalik | With the relay traffic measurement in phase G. |
| AR-08 | Report counts per target on the relay can be inflated with throwaway accounts (one report per reporter, target and category) (candidate I12, report half). | Accepted (2026-09-27) | Nothing acts on the counts automatically; only the operator reads them. Any future automatic enforcement must not rest on raw counts. | Vitalik | Before any automatic enforcement reads the counts. |
| AR-09 | A signed `KeyRequest` stays valid for the 300 s skew window, so the relay can replay a captured one (resetting a session after the 5 s cooldown), and any new identity can make us mint one-time keys, which can push a friend request's carried key bundle back to the live key exchange (candidate L6). | Accepted (2026-09-27) | A replay rule was built and broke honest session setup: peers send several identical KeyRequests within one second, and the signatures are deterministic, so a replay cannot be told from a duplicate. A relay able to replay can also just drop frames, and a session reset or a lost carried bundle only falls back to the live key exchange. | Vitalik | With the class A design. |
