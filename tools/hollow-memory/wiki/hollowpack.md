# .hollowpack — the artist shop's art container

Built 2026-08-29 for the artist shop (design record: `reports/ARTIST_SHOP_DESIGN.md`; memory `project_hollowpack_format`, `project_artist_shop_design`). Phase 1 = the store sells DRM-free art; phase 2 binds a blind-signed support credential to the art's hash.

## Format (v1)

A ZIP: `pack.json` + `files/<sha256>.webp`. Manifest fields: `format: "hollowpack"`, `version: 1`, `item {id, title, kinds}`, `artist {name, slug, url}`, `license`, `files [{role, path, sha256, bytes, w, h, animated}]`, `ext {}` (reserved for the phase-2 issuing key and catalog signature). Roles (ceilings per the 2026-09-01 encoder bump, memory `project_encoder_ceilings_bump`): `frame` (square, at most 512, animated or still -- a CEILING since the bump, so older exactly-128 packs stay valid), `avatar` (still-only, 512 ceiling), `avatar_anim` + `avatar_still` (the pair `process_user_avatar_anim` returns), `banner` (still-only, 2.5:1, 1200x480 ceiling), `banner_anim` + `banner_still`. Animated vs still is decided from BYTES (`is_animated_image`), never the extension. `item.id` defaults to the first 16 hex of sha256 over the sorted file hashes (content-addressed).

**Identity is the hash of the PROCESSED bytes.** The pack is produced only by the app's own encoders (`process_avatar_frame`, `process_avatar_image`, `process_user_avatar_anim`, `process_banner_image`, `process_user_banner_anim`) so a pack made by the tool and art the app processes itself land on the same hash (libwebp is deterministic). A lossy WebP re-encoded is a different hash, so **the importer never re-encodes**.

## Code

- `rust/hollow_core/src/hollowpack.rs`: format structs (`#[serde(default)]` on every optional field, unknown fields ignored, `format`/`version` checked), `process_source`, `build_pack`, `catalog_entry`, `read_manifest`, `verify_pack` / `verify_pack_file` (the ONE trust boundary; see `security_write_gates.md` §2).
- `rust/hollow_art/` (since 2026-09-02): the crate the CLI is built from. It has NO code of its own: `src/lib.rs` and `src/node/mod.rs` `#[path]`-include `hollow_core/src/hollowpack.rs`, `node/image_convert.rs` and `node/webp_anim.rs`, so the tool compiles the app's exact encoder sources without dragging MLS/SQLCipher/WebRTC along, and its `Cargo.lock` was seeded from hollow_core's so `image`/`image-webp`/`webp-animation`/`libwebp-sys2`/`zip` resolve to the versions the app ships (re-seed it when hollow_core bumps one). The included files' `#[cfg(test)]` modules reach hollow_core-only modules, so tests run in hollow_core (`cargo nextest run --lib hollowpack image_convert`), never in hollow_art. The old `packtool` feature and `[[bin]]` in hollow_core are gone.
- `rust/hollow_art/src/main.rs`: the CLI, `pack` / `inspect` / `process` / `version`. Build: `cd rust/hollow_art && cargo build --release` (Windows, ~25 s, `target/release/hollowpack.exe`; a copy lives at `anonlisten-sites/shop/.data/bin/hollowpack.exe` for the shop's local dev server). **Shop host build:** `pip install ziglang cargo-zigbuild`, `rustup target add x86_64-unknown-linux-musl`, then `cargo zigbuild --release --target x86_64-unknown-linux-musl` (zig 0.16 + cargo-zigbuild 0.23 verified; static musl, 2.7 MB, runs on the host's glibc-2.28 CloudLinux). Installed at `~/domains/anonlisten.com/shop/data/bin/hollowpack` on Hostinger (outside `hbuilds`, so a deploy never removes it); a 1 MB JPEG encodes in ~0.3 s there. `pack` flags: `--emit-entry <json>` (the catalog entry the shop ingests), `--emit-files <dir>` (every processed file as `<dir>/<sha256>.webp`), and the buyer's download `--delivery <zip>` = the pack at the root (named after `--out`) + each `--original <path>` under `originals/<basename>` (basename only, duplicates refused, STORED) + `--readme <file>` as `README.txt` (deflated). Exit 0 on success, 1 with `hollowpack: <reason>` on stderr otherwise; `pack` prints one `encoded ...` line per processed file and one `wrote ...` line per artifact on stdout.
- FFI `import_hollowpack(path) -> HollowpackImport` and `list_owned_art()` in `api/network.rs`: verify, then store bytes AS-IS on the asset rail (kind `frame` for frames, kind `profile` for every avatar/banner role, stills included) and record `owned_art(hash, role, item_id, title, artist_name, artist_slug, artist_url, license, imported_at)` in `storage/messages.rs`. Importing does NOT wear anything; "wear it" is a later step that reads the still back off the rail and sets the profile the way the pickers do.
- `image_convert::validate_frame_centre` re-applies the see-through-centre gate to already-encoded frame bytes.

## Verification (import and `inspect` are the same call)

Caps first (8 files, 4 MB each, 16 MB total, 20 MB zip, 64 KB manifest; the biggest legal single asset is a 2 MB animated avatar or banner), then per file: recomputed sha256 must match, the WebP must decode, dimensions within the role's ceiling (frame: square and at most 512), animated roles animate and still roles do not, frames pass the centre gate. A manifest that disagrees with the bytes about size, dims or animation is REFUSED, never silently corrected. Nothing is written by a manifest-supplied name. 17 unit tests (`cargo nextest run --lib hollowpack`).

## The shop runs it (server-side approval, 2026-09-02)

The keeper no longer runs the CLI by hand. In `anonlisten-sites/shop/`, an artist marks every submitted file with a ROLE (`avatar`, `banner`, `frame`, or `source` = ships only; `src/lib/submission_roles.js`, validated by `checkSubmissionRoles` with magic-byte sniffing), and **Approve and list** on `/admin/ingest` does the whole act in `src/lib/server/approve.js`: `packtool.js` execFile's the binary at `config.hollowpackBin` (`HOLLOWPACK_BIN`, default `<SHOP_DATA_DIR>/bin/hollowpack`, 90 s timeout under the host's 120 s cap) with `pack --file <role>=<path> ... --emit-entry --emit-files` (the `--delivery` zip exists in the CLI but the shop no longer builds one: the originals go on the Creem product as they are, downloaded one by one from the listing page), feeds the emitted entry + WebPs through the SAME `ingestSubmission` a hand-made pack takes (hash recompute, row `submitted` to `approved` in one transaction), records `listings.pack_file` (migration 6, relative `packs/<id>/<stem>.hollowpack`; `delivery_file` stays NULL now), then `createProductFor` (Creem `POST /v1/products`: onetime, USD, tax exclusive, digital-goods-service, `image_url` = the shop's `/art/<hash>` when the origin is https). The SPLIT is NOT part of the button (Vitalik, 2026-09-02): `createSplitFor` runs from the listing page's own button once the product carries license keys + files, because creating the split is what emails the artist the invite (store id if known, else the artist's sealed Creem address `artists.creem_email_enc`, else their sign-in address; cleared by `setArtistStore`). What the Creem API cannot set, license keys and the delivery file, is a checklist on `/admin/listing/<id>` read back off `GET /v1/products?product_id=` (`features[].type` = `licenseKey` / `file`). The manual door (entry JSON + WebPs) stays at the bottom of the submissions page. Never encode in JavaScript (sharp) for a listing: identity is the app encoder's bytes.
