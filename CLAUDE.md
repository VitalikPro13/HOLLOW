# HOLLOW — Project Instructions for Claude Code

## What Is This
Hollow is a fully distributed, encrypted Discord alternative. No central servers. Members collectively host the server. See `HOLLOW_PLAN.md` for the full architecture, phase history, and current TODO checklist.

## Tech Stack
- **UI:** Flutter (Dart) — all platforms (Windows, macOS, Linux, Android, iOS, Web)
- **Backend:** Rust via `flutter_rust_bridge` v2.11.1 FFI
- **Networking:** WSS relay (signaling + text/CRDT/MLS) + WebRTC data channels (files/shards P2P) + WebRTC media (voice/video P2P). libp2p fully removed.
- **E2EE:** vodozemac (Olm/Double Ratchet) for DMs, OpenMLS 0.8 for servers, SFrame (AES-128-GCM) for voice/video/screen share
- **Local DB:** SQLCipher (encrypted SQLite)
- **Identity:** Ed25519 keypairs via BIP-39 mnemonic (ed25519-dalek, NativeKeypair)
- **Org ID:** com.anonlisten
- **Project name:** hollow

Output (signed installer + zip) lands in `installer\Output\` (gitignored). See `reference_certum_signing_procedure` + `project_windows_installer_pipeline` memories. ## Hollow Design System (Phase 2.75)
All UI uses custom Hollow widgets — no Material defaults.

- **HollowPressable:** Press: opacity 0.85 + scale 0.98 (spring). Hover: color transition 150ms + shadow lift. `subtle` mode for list items.
- **HollowButton:** 4 variants: `.filled()`, `.ghost()`, `.outline()`, `.danger()`. Props: `onPressed`, `child`, `icon`, `expand`, `compact`.
- **HollowTextField:** `OutlineInputBorder`, animated border (→accent on focus, →error on error), focus glow. Optional `prefixIcon`, `borderRadius`, `isDense`, `showCounter`.
- **HollowDialog:** `showHollowDialog()` — scale 0.95→1.0 + fade, full-screen glassmorphism blur (0→12 sigma).
- **HollowTooltip:** Overlay-based, 400ms delay, fade+slide entrance.
- **HollowToast:** Slide-up + fade, auto-dismiss. Three types: success/error/info. One visible at a time.
- **HollowToggle:** Spring physics thumb, color crossfade track.
- **StatusDot:** Optional `pulse` for breathing glow (3s cycle).

## Key Architecture Notes
- **Node module structure:** `swarm.rs` is the event loop dispatcher; domain logic lives in focused modules (`crypto_handler`, `sync_handler`, `message_ops`, `social`, `vault_ops`, `file_handler`, `voice_handler`, `gossip_relay`). Types/enums are in `types.rs`. Each module exports `pub(crate) async fn handle_*()` functions called from swarm.rs match arms. Functions take individual state variables as parameters (no SwarmContext struct — deferred due to borrow checker constraints with crypto helpers).
- **Persistence actors:** `CrdtStore` (`node/crdt_store.rs`) and `CryptoStore` (`crypto/store.rs`) own long-lived SQLCipher connections in `spawn_blocking` threads. Fire-and-forget via mpsc channels. CrdtStore uses batch-drain (blocking_recv + try_recv loop) to coalesce multiple CRDT ops into one DB write per server. All sync_handler save sites use CrdtStore. MLS state persistence uses CryptoStore. Never open `MessageStore::open()` in sync handlers.
- **Peer state tracking in swarm.rs:** `ws_room_peers` (room → peer set), `synced_peers` (HashSet<String>). WS PeerJoined triggers key exchange + sync. 30s keepalive ping in ws_client.rs.
- **Relay domain (self-hosting):** Configurable via `relayDomainProvider` (Dart) + `set_relay_url()` FFI (Rust). Persisted in SQLCipher. Default: `relay.anonlisten.com`. All WS/signaling/STUN/TURN URLs derive from this domain.
- **Event streaming:** Rust→Dart via `StreamSink` (flutter_rust_bridge). `watch_network_events()` in `api/network.rs`, `EventStreamNotifier` in `event_provider.dart`.
- **Profile/avatar loading:** Profiles load WITHOUT blobs at startup (`getAllProfilesLight()`). Avatar bytes lazy-load on-demand via `AvatarNotifier` in `avatar_provider.dart` (same pattern as `ServerAvatarNotifier`). Banner bytes via `bannerProvider` (FutureProvider.family). `HollowAvatar` is a `ConsumerWidget` that auto-fetches from avatar cache — don't pass `imageBytes:` from profile data. `ProfileUpdated` event invalidates both caches.
- **Navigation shell:** Two layout modes (persisted via `layoutModeProvider`): Dock mode (default, FriendsBar + BottomBar) and Classic mode (Discord-like 4-panel). Mobile: bottom nav with single-panel views. Vitalik uses Dock mode — put new UI in `bottom_bar.dart`.
- **Window chrome:** `window_manager` ^0.5.1, `setAsFrameless()`, custom 32px title bar.
- **Theme:** `HollowTheme.dark()`/`.light()` + `darkWithHue()`/`lightWithHue()`. `themeModeProvider` persisted to SQLCipher.
- **Icons:** `lucide_icons_flutter: ^3.1.14`. All `LucideIcons.*` (camelCase). Uses `alertTriangle`/`alertCircle`. No `cloudCheck` — uses `cloud`. Brand icons use vendored `lib/src/core/brand_icons.dart` (`BrandIcons.*`, `BrandIconColors.*`) with `assets/fonts/SimpleIcons.ttf`.
- **Identity at-rest protection:** Two opt-in modes (Settings > Security): password (Argon2id + AES-256-GCM, blocks app launch) or OS keychain (Windows Credential Manager + DPAPI fallback / macOS Keychain, silent unlock). `unlock_identity()` must be called before any identity/DB operation. Recovery: 24-word mnemonic. See `project_identity_protection_v2.md` for byte format and implementation details.
- **License key system:** Relay loads `keys.json` (enabled toggle + key list), validates during WS auth, hot-reloads every 30s with active connection revocation. App checks `/relay-status` on startup, shows key dialog if required, caches key in SQLCipher via `set_license_key()` FFI.
- **Temporary nicknames:** Ephemeral relay-scoped nicknames for friend requests. RAM only (`nickname_to_peer`/`peer_to_nickname` maps in `RelayState`), released on disconnect. Relay handles `claim_nickname`/`release_nickname`/`resolve_nickname` text messages. Rust does two-step resolution (resolve → normal friend request). UI auto-detects peer ID (`12D3KooW` prefix) vs nickname in a unified input. Provider: `temporaryNicknameProvider`, resets on `RelayDisconnected`.
- **Window title bar:** `WindowTitleBar` lives in `MaterialApp.builder` (above Navigator), NOT inside `HollowShell`. Navigator child wrapped in `ClipRect` to prevent `BackdropFilter` blur bleed. Never move the title bar back inside the shell.
- **Logging:** `hollow_log!` macro → stderr + `hollow_debug.log` (release-safe, 10MB rotation). `hollow_crash.log` captures Flutter/platform errors (5MB rotation).
- **Relay:** uWebSockets C++ relay (`relay-uws/`) on OVH VPS, native OpenSSL TLS, port 443. Domain: `relay.anonlisten.com`. **No backpressure soft limit, no binary rate limit** — removed because they silently dropped messages. `maxPayloadLength`=64MB — NEVER lower (silently kills connections). `maxBackpressure`=64MB (hard). DoS protection: Ed25519 auth + license key revocation + per-IP limits. Topic routing: `0x07` frame with channel_id, `0x03` universal broadcast. See `feedback_relay_rules.md` for details.
- **Storage layout:** `~/.hollow/files/` (full-replication), `~/.hollow/vault/` (erasure-coded shards), `~/.hollow/vault_cache/` (LRU-evicted, 1GB cap).

## Coding Conventions
- Dart: follow `flutter_lints` / `analysis_options.yaml`. Rust: follow `cargo clippy`.
- File naming: snake_case for Dart and Rust files.
- No Electron, no Node.js, no web frameworks — Flutter only for UI.
- **NEVER pass `WidgetRef ref` as a constructor parameter** to child widgets. Always use `ConsumerWidget` or `ConsumerStatefulWidget` instead. Passing `ref` causes cascade rebuilds.
- Use `AnimatedOpacity` (GPU-composited) for per-item opacity. Never use the `Opacity` widget.
- **CRITICAL — Backward-compatible DB schema:** ALWAYS add `#[serde(default)]` to ANY new field added to a persisted Rust struct (e.g., `ServerState`, any struct stored as JSON in SQLCipher). Without it, old data lacking the new field fails to deserialize and silently disappears (servers vanish, data lost).
- **CRITICAL — flutter_webrtc native: use `sourceId` for ALL input device selection (audio AND video).** Correct pattern: `{'optional': [{'sourceId': deviceId}], 'width': ..., 'height': ...}`. `{'deviceId': ...}` is silently ignored.
- **CRITICAL — server switching must batch provider writes atomically.** `channelListProvider`, `channelLayoutProvider`, `selectedServerProvider`, and `selectedChannelProvider` must all update in a single synchronous block. See `server_strip.dart:_selectServer` for the canonical pattern.
- **CRITICAL — TURN ICE config: split URIs into separate entries.** flutter_webrtc's native `CreateIceServers` has a single `uri` field per `IceServer` struct. Always map each TURN URI to its own entry.
- **CRITICAL — MLS epoch staleness after reconnection.** Sync requests must use plaintext `HavenMessage`. CRDT broadcast must fall back to plaintext on MLS failure. See `feedback_mls_patterns.md` for all 8 MLS rules.
- **CRITICAL — WS send failures must trigger reconnection.** `send_command()` in `ws_client.rs` returns `bool`. If false (TCP write failed), the main loop must break, push the failed command to `pending_commands`, and reconnect. Never silently discard send errors.
- **CRITICAL — mobile selection providers cleared in `.then()`, not `dispose()`.** See `feedback_mobile_ui_patterns.md` for full pattern.
- **CRITICAL — in-memory message lists must dedup by `message_id`.** `chat_provider`/`channel_chat_provider` `_addMessage`/`receiveMessage` skip when a non-null `message_id` already exists — the same message arrives via both `loadHistory` (DB, possibly written by the FCM push-fetch node) AND a live network event. Naive append shows it twice even when the DB is correct. See `feedback_ui_dedup_by_message_id.md`.
- **CRITICAL — multi-device device-vs-master routing (Phase 6).** A person has several DEVICE peer_ids that all resolve to ONE MASTER identity. The relay reports DEVICE ids (rooms, `peersProvider`, `connStatus`, typing events); friend/DM/profile/presence UI keys on the MASTER (`friend.peerId`). Two iron rules: **(1) per-person UI/lookups must collapse device→master** (Rust `resolver::resolve`/`same_identity`; Dart `deviceLinkProvider.identityOf`/`onlineIdentitiesProvider`/`identityIsOnline`) — a direct `map[friend.master]` silently never matches a multi-device friend (broke presence dots, Home column, chat-header Encrypted, typing display). **(2) SENDS must target a DEVICE, never the bare master** — the master authenticates as NO socket, so anything addressed to it is silently dropped (broke DM messages, DM typing). Fan out via `resolver::devices_for(master)` UNIONed with live DM-room peers resolving to that master. **`dm_room_code` is PURE — never resolve inside it** (room must be `f(my_master, friend_identity)` so two friends always agree; resolving there diverged the room per-side → keying errors even for plain friends). Sibling self-echo DMs carry `is_own`/`convo` so they render OUTGOING under the right thread. **DM peer-fallback (Step 5 second half, LIVE 2026-06-18):** a multi-device requester sets `DmSyncRequest{both_directions:true}` so a FRIEND re-serves your OWN messages sent from another (offline) device (`get_dm_messages_for_sibling`, gated on `!devices_for(local_master).is_empty()`) — otherwise stranded. **`DmSyncItem.mine` is RESPONDER-RELATIVE:** a cross-IDENTITY direction field is sender-relative, so the receiver re-orients it (`is_mine = if same_identity(sender) { mine } else { !mine }`) for BOTH insert AND sig context; a cross-DEVICE (same-identity sibling) field is NOT inverted. Forgetting this rendered backfilled DMs on the wrong side + flooded sig-verify failures. **Servers/MLS ARE multi-device as of Step 6 (LIVE 2026-06-18)** — both of a person's devices hold their own MLS leaf and member panels DO collapse devices→master now. Fresh single-device installs are byte-for-byte pre-multi-device (resolver returns self). See `project_multidevice_step6_mls_leaves.md`, `project_multidevice_migration_state.md`, `feedback_relay_ghost_connection_eviction.md`, `reports/MULTI_DEVICE_IMPLEMENTATION_TRACKER.md`.
- **CRITICAL — multi-device SERVERS/MLS (Step 6).** MLS leaf credential = the bare `device_peer_id` (each device its own distinct leaf; `MlsManager::new(&device_peer_id)`). CRDT `ServerState.members` is MASTER-keyed (joiner resolved device→master at `MemberAdded`; `canonicalize_members` folds legacy device-keyed entries on load/sync). **THE INVARIANT:** `state.members` master-keyed, `mls.group_members()` device-keyed → every MLS↔CRDT compare bridges through `resolver`/`same_identity`; use `ServerState::is_member()` not `members.contains_key()`. A `crdt/mod.rs` resolver-hook chokepoint makes `get_role`/`has_permission`/`is_banned`/`is_member` collapse device→master internally (one fix for ~24 lookup sites). Every targeted member SEND fans master→online devices via `crypto_handler::send_raw_to_identity` (the bare master is in no room → dropped). **A LINKED SIBLING MUST regenerate its OWN MLS signer/credential** — the snapshot import copies the source's `mls_identity` table; reusing it = `DuplicateSignatureKey`/`CannotDecryptOwnMessage` (`import_pending_link` clears it; startup net regenerates iff `cred != device && (cred != master || has_sibling)` — NEVER re-key a sole owner). Post-join MLS bootstrap sends the KeyPackage to the SyncResponse responder (`peer_str`) directly, NOT via resolver-based election (resolver is cold on a fresh join). Channel messages need `subscribeChannels` on EVERY channel-open (relay topic-routes `SendToRoomTopic`; subscribed socket only gets its topic set) — `ref.listen(selectedChannelProvider)` in hollow_shell + `mobile_shell._openChannel`. See `project_multidevice_step6_mls_leaves.md`, `feedback_mls_sibling_identity_collision.md`.
- **CRITICAL — multi-device REVOCATION + ghost fan-out (Steps 7/8, LIVE 2026-06-18).** Device list now carries a master-signed `revoked: Vec<String>` tombstone array (signing payload gained `:{sorted_revoked_csv}`; max-version-wins — higher version adds AND un-revokes, replay can't shrink). **Revocation is manual-only** (`NodeCommand::RevokeDevice`/FFI `revoke_device`; any device-you-control revokes another — all hold the master key, no "promotion"). The tombstone MUST be sent **to the revoked device FIRST** (`handle_revoke_device`) so its ingest fires `NetworkEvent::SelfRevoked` → `event_provider._selfNuke()` (`stash_pending_wipe` FIRST, then best-effort `overlayState:` toast — NEVER plain `HollowToast.show(ctx)`, it throws from a navigator-key context and aborts the wipe) → data-dir wipe + relaunch to Welcome. `ingest_device_list` returns `IngestOutcome { our_devices_grew, newly_revoked }`; `swarm::enforce_device_revocations` drops the Olm session (+ erases the persisted pickle via `CryptoStore::delete_session`) and, coordinator-only, removes the single MLS leaf via `pending_mls_removals`. **GHOST FAN-OUT (the load-bearing fix):** the DM/file fan-out (`message_ops::collect_target_devices`) targets `devices_for(master)` filtered to ids **CURRENTLY IN A ROOM** — a dead ghost (re-link cycles mint new ids; union-merge never prunes) keeps a STALE session so `has_session` is NOT enough; room-presence is the liveness test. Single-device offline FCM push preserved via `fallback_self`. **Dart:** DM unread + notifications resolve `fromPeer`→master (`identityOf`) or the nav pill sticks counting a dead device. **Phantom-chat guard:** `resolver::mark_revoked`/`is_revoked`; DM+typing receive paths drop messages from a revoked-but-alive device (after `forget` its id resolves-to-self → would spawn a standalone "unknown peer" chat). **Step 8 Devices panel** (Settings → Security → Your Devices, desktop `user_settings_dialog` + mobile `mobile_settings_tab`): lists my devices (shortened id, online, local editable label via `device_labels` table, "This device", "Remove device" → revoke), offline-unlabeled ghosts behind "Show all (N offline)". See `feedback_ghost_device_fanout.md`, `feedback_toast_from_nonwidget_overlaystate.md`.
- **CRITICAL — device linking / snapshot sync (Step 4, LIVE).** A new device pulls the full identity+DB from an online one via a 6-char code (no QR). **The transfer REUSES the `.hollow` backup pipeline end-to-end, NOT a parallel path:** sender `export_backup_bytes(code,…)` (the link CODE is the passphrase) → stream as `StreamKind::LinkSnapshot` → receiver `stash_pending_link(blob, code)` writes `pending_link.hollow`+`.code` and RESTARTS → next launch `_bootstrap` (FIRST, before `hasIdentity()`) `has_pending_link()`→`import_pending_link()` (deletes throwaway identity, then `import_backup_bytes` — identical to a manual restore). **NEVER import in-place while the node runs:** the original `import_snapshot_bytes` fought the live SQLCipher connection + WAL + a protection-mismatched throwaway `identity.device` → "Loading… forever". `import_backup` works only because it runs pre-node-start. The empty device uses a THROWAWAY identity just to get a relay socket; the snapshot overwrites it (the relay needs no new "guest" mode). 6-char code = temp-nickname RAM-map clone on the relay (`link:{code}` rendezvous room, 5-min TTL, one-shot). Sender progress is an indeterminate spinner (fire-and-forget push), receiver has the real byte bar. See `feedback_link_import_identity_device.md`, `project_multidevice_step4_link_design.md`.
- **CRITICAL — push notifications (FCM Tier 1/2).** Relay buffers offline DMs in RAM (`offline_buffer`, 100 text + 1 image/peer, 24h TTL) and replays on DM-room join — Tier 2 fetch can't get the triggering message otherwise (relay is a dumb pipe). `fetch.rs` parses binary `0x06` frames (not text). **Offline images:** sender inlines AES-encrypted bytes into the FileHeader → `0x08 SendDirectImage` frame (must target `dm_room_code()` directly — offline peers are in no room) → relay buffers under the image cap → fetch decrypts, writes the file, AND inserts the `messages` row itself (companion text DM is dropped to offline peers). The notification shows a lightweight line — `📷 Image` (captionless) or `📷 <caption>` — NOT a BigPicture preview (removed: decode+downscale on the notif thread was too slow; image still syncs to DB). **Captioned offline image:** the caption is sent EXACTLY ONCE via `crypto_handler::send_encrypted_text_to_peer` (0x04, text cap) AFTER the FileHeader — never via `send_encrypted_message` for an offline image (it encrypts-then-discards, burning an Olm ratchet slot the receiver never sees → decrypt gap). **Signatures:** the row sig rides on the DirectMessage envelope; for offline images the FileHeader must carry `sig`/`pk` (captionless: only sig carrier, signed over `[file:<id>]`), and `promote_file_sentinel_to_caption` UPDATEs text+sig+pk together (else "Unsigned"). **Notification UX (Android done):** post ONE populated banner after the fetch (no generic flash + swap); per-peer card (`sender.hashCode`) + InboxStyle last-3 + Android N-count; `groupKey:'hollow_dm_group'` + silent summary (`GroupAlertBehavior.children`) bundles multiple peers; `dismissPeerNotification()` clears the summary when no children remain. Status-bar icon MUST be a monochrome white silhouette (`@drawable/ic_stat_hollow`) — `@mipmap/ic_launcher` renders as a white blob (Android keeps only alpha). Launcher icon via `flutter_launcher_icons` from `assets/hollow_icon_android.png` (square full-bleed render of `hollow_main_logo.svg`; solid `#0D0F14` adaptive bg). See `feedback_fcm_image_invisible_bubble.md`, `project_push_notification_implementation.md`. Background isolates: NEVER trust `RustLib.init()` to be idempotent (reused isolate throws "twice" → treat as ready) and NEVER call `load_or_create_identity()` (use `load_existing_identity()` — generating yields wrong peer_id/DB passphrase). `log_path()` honors `set_data_dir()` so mobile `hollow_debug.log` writes. See `project_push_notification_implementation.md`, `feedback_rustlib_init_not_idempotent.md`. Firebase config files (`google-services.json`, `GoogleService-Info.plist`) are gitignored — public repo, contributors bring their own project. **iOS specifics:** classic non-UIScene AppDelegate (`register(with: self)`) + firebase pinned below the iOS-SDK-v12 break (`firebase_core ^3.15.2`, `firebase_messaging ^15.2.10`) to keep iOS 13 — UIScene would force iOS 15 for no gain. iOS push is a VISIBLE ALERT (`apns-priority:10`, `apns-push-type:alert`, generic `body:'New message'`, `mutable-content:1`, `content-available:1`) — NOT a pure silent push (Apple throttles those).
